FoundationPose — bug log
=========================
Upstream pinned at a1b694b (NVlabs/FoundationPose, main).
Scope: 6-DoF pose estimation and tracking of the object OpenMask3D selects. Adapted, not
reimplemented — its two networks are plain PyTorch and only the renderer is CUDA-only.


[1] One file made the whole project unimportable off-GPU
----------------------------------------------------------
Date:        2026-09-21
Fingerprint: `from estimater import FoundationPose` -> ModuleNotFoundError: nvdiffrast
             (then pytorch3d), on a box with neither.

Cause:       `Utils.py` imports `nvdiffrast.torch` and six `pytorch3d` symbols at module
             scope, and `estimater.py` does `from Utils import *`. Upstream already
             guards kornia, mycpp, bundlesdf.mycuda and warp in try/except — these two
             are simply not guarded. The cost is out of proportion to the cause:
             learning/models/{score,refine}_network.py and network_modules.py contain
             ZERO CUDA-only imports, so the networks that ARE the checkpoint were
             unreachable because of a rasteriser they never call at construction time.

Fix:         `compat.py`, registry-hook style per CLAUDE.md — nothing patches vendored
             source. Absent packages are registered in sys.modules as ModuleType
             subclasses that import cleanly and raise on first attribute access. Same
             contract as droidSLAM_monocular/compat.py gives lietorch.

             The split is deliberate:
               - nvdiffrast: CUDA-only rasteriser, no CPU build -> always stubbed here.
               - pytorch3d: HAS a CPU build, just painful on Apple Silicon -> stubbed
                 only when absent, so a machine that has it uses the real one.

Why not a working stub: FoundationPose renders each pose hypothesis and scores it
against the observed crop. A rasteriser returning zeros or plausible geometry yields a
confident, wrong pose, and a pose is the canonical value nothing downstream can
sanity-check. CLAUDE.md: "If it cannot run locally, it must raise locally."


[2] The import guard reported its own stubs as the real thing
---------------------------------------------------------------
Date:        2026-09-21
Fingerprint: `ensure_importable()` returned {'nvdiffrast': False, 'pytorch3d': False} on
             the first call and {'nvdiffrast': True, 'pytorch3d': True} on the second.
             `describe()` then printed "all render dependencies present; pose estimation
             can actually run" on a Mac with no renderer.

Cause:       `_available()` probed with `__import__(name)`. Once the placeholder is in
             sys.modules that import SUCCEEDS, so every call after the first concluded
             the real package was present.

Fix:         `_available` now returns False when sys.modules holds a MissingModule for
             that name, both before and after the probe.

Why it mattered: this is the exact failure class the guard exists to prevent, reproduced
inside the guard. "The checkpoint loaded" means something different on a box where the
renderer was a placeholder, and the status dict is how a caller is supposed to tell.
A status that lies is worse than no status.

Status:      Fixed. 6 tests pass, including one that calls ensure_importable() twice and
             asserts the status does not drift.

[4] A 72 cm pose error blamed on a frame convention that does not exist
------------------------------------------------------------------------
Date:        2026-09-23
Fingerprint: `register()` on our TSDF mesh returns t = [0.567, 0.424, 2.730] m while the
             segmentation centroid it should match is at [0.388, 0.582, 2.050] m —
             72.14 cm apart, with a 2.08 cm world-frame tracking spread saying the
             tracker is perfectly steady.

Cause (of the wrong diagnosis, which is the bug):
             `estimater.reset_object` computes `model_center = (min+max)/2` and subtracts
             it from the mesh vertices. Read alone, that says the returned pose is the
             bbox centre's position whatever origin you supplied. On this instance the
             Poisson surface over a one-sided shell is lopsided, so its bbox centre sits
             52.9 cm from its point centroid — close enough to 72 cm to look like the
             explanation. It is not. `estimater.py:233` un-centres the answer on the way
             out (`best_pose = poses[0] @ get_tf_to_centered_mesh()`), so `register()`
             returns the pose of the mesh AS SUPPLIED. The subtraction is internal and
             already compensated. Half of the relevant code was read.

Fix:         Reverted the re-centring in pipeline/tools/build_pose_bundle.py. The mesh
             keeps its point-centroid origin, which is what the residual is measured
             against.

Metric before/after — the change made it WORSE, which is what identified it:
             residual vs the origin actually supplied:  72.14 cm  ->  112.83 cm

What the failed fix bought, which is why it is not merely an error:
             Moving the origin a known 52.9 cm is a controlled probe. FoundationPose's
             answer moved 53.5 cm — correct MAGNITUDE, confirming the compensation works
             — but 99.5 deg away from the direction the map predicts. Both vectors are
             the same offset in the camera frame, one rotated by the estimate and one by
             the true camera rotation, so that angle is a LOWER BOUND on the rotation
             error. The 72 cm was never a translation problem: the orientation is
             essentially undetermined, and the translation residual is what that looks
             like when measured at a point offset from the rotation centre.

             A >= 99 deg rotation error is unsurprising for this input — a one-sided
             Poisson shell seen through a 695 px mask carries almost no signal to fix an
             orientation — but "unsurprising" is not "measured on the right input", so
             r12 runs upstream's own demo_data/mustard0 through the same code path. A
             small residual there convicts our bundle; a large one convicts the port.

Consequence: the 2.08 cm tracking spread was being read as reassurance. It is a
             consistency check, not an accuracy one — a tracker locked onto a wrong pose
             holds it exactly as steadily. pipeline/tools/e2e_pose.py now gates on
             translation AND rotation AND depth before any pose reaches the world model,
             because the position-only fallback is honestly uninformative about rotation
             whereas a confident wrong rotation gets acted on.

[6] A diagnostic metric that did not survive its own control
--------------------------------------------------------------
Date:        2026-09-23
Fingerprint: r13 reported the scorer's spread over 252 rotation hypotheses — range 1.75,
             std 0.196, 48/252 within 1% of the top — and concluded the orientation was
             unidentifiable, "the summit of a plateau, not a peak". That was published
             in RESULTS.md and README.md before the control ran.

Cause:       The scores are computed AFTER refinement. Every hypothesis is refined
             toward the observation first, so hypotheses that converge onto the SAME
             pose legitimately end up with the same score. A flat top therefore means
             agreement, not ambiguity — the exact opposite of the reading given.

Refuted by:  mustard0, which returns a CORRECT pose, is flatter at the top than ours:

                                  ours      mustard0
                margin over top-2  0.5000    0.0000   (an exact tie)
                within 1% of top   48/252    91/252

             A metric on which the known-good case scores worse than the known-bad case
             does not discriminate, whatever story can be told about it.

Fix:         r14 replaces it with pose clustering — pairwise geodesic angle among the
             top-16 refined poses. If they are one orientation reached from different
             starts, the angles are small and the estimate is determined; if they are
             scattered, the scorer is choosing between orientations it cannot tell
             apart. Measures the quantity the earlier metric was assumed to proxy.

Lesson kept: the metric was designed, run, interpreted and published in one pass, and
             the control that would have checked it was already queued. Reading a result
             before its control lands is how a plausible story gets into a README.


[7] A gate check that could not fire on the input it was written for
----------------------------------------------------------------------
Date:        2026-09-23
Fingerprint: e2e_pose.py refused `chair_4` on translation and rotation, never on depth,
             despite the pose sitting 60.8 cm behind the measured surface.

Cause:       The depth tolerance was half the instance's 3-D EXTENT. `chair_4` is a
             coarse proposal spanning 1.58 m, so the tolerance was 78.9 cm and a 60.8 cm
             error passed. The bound was not wrong, it was vacuous — and it scaled with
             the segmentation's opinion of the object's size, which is the very thing
             the depth check exists not to trust.

Fix:         Bound by the depth the camera ACTUALLY SEES: 5th-95th percentile of masked
             depth, plus a 10 cm margin. On these frames the visible surface is a
             13.4 cm slab, so the tolerance drops 78.9 -> 23.4 cm and the check fires.
             Now uses only the depth image, independent of the segmentation.

Metric before/after:  depth check on chair_4:  PASSES (60.8 < 78.9)  ->  FAILS
                      reasons reported per frame:  2  ->  3

Also corrected: an earlier write-up of this run claimed all three checks fired
"including the depth one". They did not. The gate refused on two.


[8] The input blamed on fusion density was eight frames chosen in arrival order
--------------------------------------------------------------------------------
Date:        2026-10-04
Fingerprint: The pose bundle's masks were 655-954 px, where a 1.58 m object at 2.0 m
             under fx=535 subtends ~410 px across. Published diagnosis: "a one-sided
             Poisson shell seen through a sparse partial view", fix "a denser fusion
             (smaller --stride)". Both wrong.

Cause:       `build_pose_bundle.py` walked the sequence in order and kept the first 8
             frames in which >= 50 instance points survived its depth test. 50 of 1,142
             is a 4.4% floor, so the rule is not "is the object visible here" but "is
             anything here at all" -- and on a SLAM-posed sequence the earliest frames
             are also the worst-posed ones. Measured across all 827 usable frames:

                                       chosen frames 1-9      sequence best
               instance corroborated    11-17%                 73-74%
               median signed residual   -37 to -62 cm          -1.1 cm
               camera baseline, 8 fr    3.4 cm                 20.8 cm available
               view-angle span, 8 fr    1.1 deg

             The SIGN is what convicts the selector rather than the map. A point BEHIND
             the measured surface is occluded, which is ordinary. These points were in
             FRONT of it by half a metre -- not occlusion, since had the object been
             there it is what the depth camera would have hit. The fused map and the
             depth images agree to -1.1 cm median on a frame where the chair is actually
             in view, so the fusion was never the limit.

             A second, independent defect in the same function: the mask was a SPLAT of
             projected points closed with a 9x9 kernel. The cloud is voxel-sparse, so
             even a perfect frame splats ~840 points into a region subtending tens of
             thousands of pixels -- 4.7% of its own bounding box.

             A third: the mesh was cut from the raw member set, skipping the density
             rejection every other stage applies, so 14 strays stretched the instance
             0.99 -> 0.59 m in height and Poisson (cropped to that box) built a slab of
             invented surface in the empty 40 cm.

Fix:         Three changes, all in `build_pose_bundle.py`, with tests in
             `pipeline/tests/test_pose_bundle.py`:
               - rank every frame by corroborated points; anchor `register()` on the
                 best; fill the rest as a forward chain within `--max-step` (0.15 m) so
                 `track_one` still has a tractable step, and at least `--min-step`
                 (0.03 m) apart so the baseline is not one view eight times;
               - refuse outright below `--min-visible` (0.35) rather than emit a bundle
                 whose badness nothing downstream can see;
               - replace the splat with a depth-verified dense fill: rasterise the
                 instance's own depth, take a local nearest-surface estimate, keep every
                 pixel whose MEASURED depth agrees. Bounded by the depth image, so
                 interiors fill and background does not;
               - apply `reject_outliers` before meshing.

Metric before/after (same fusion, same mesh pipeline, same instance):

               mask pixels, mean            842  ->  6,908     (8.2x)
               mask fill of its bbox        4.7% ->  69.0%
               instance corroborated      11-17% ->  64-74%
               camera baseline span       3.4 cm ->  20.8 cm
               max tracking step                ->  5.0 cm   (under the 15 cm cap)
               depth slab under mask     13.2 cm ->  17.7 cm  (NOT bleeding: the mask
                                                      grew 8x, the depth it covers did
                                                      not)
               mesh triangles              9,657 ->  8,189
               instance height              0.99 ->  0.59 m

             For scale: mustard0, the control that registers CORRECTLY through this same
             code path, has a 3,252 px mask. The bundle was at 26% of that and is now at
             212%.

NOT YET MEASURED: whether this moves the 175.63 deg rotation error. It cannot be known
here -- `register()` needs nvdiffrast. The claim made is about the INPUT only, and the
bundle fingerprint below exists so the re-run cannot be confused with the old one.

Also fixed, same entry: `pose_result.json` is produced on a T4 and copied back by hand,
and the pose stage checked only that the target NAME matched. A rebuilt bundle keeps its
target and changes every frame under it, so a stale result compared equal and was read
as current. `bundle.json` now carries a `fingerprint` over mesh, frame identities and
camera poses; `fp.py` copies it into the result; `e2e_pose.py` refuses a mismatch. This
is [S22] from the simulator track in a different file -- comparability has to be a
property of the recorded artefacts, not of remembering which run produced what. The
result on disk is correctly refused as stale by this check.

Lesson kept: the published diagnosis named the right SYMPTOM (695 px) and the wrong
cause, and the proposed fix (refuse a denser fusion) would have cost hours of TSDF
memory to move a number that frame selection moved 8x for free. What separated them was
one measurement nobody had taken -- the same statistic, computed on every frame instead
of on the eight already in hand. This is the same shape as W7 in the simulator track,
where a planner fix was designed for what turned out to be contact stiffness.


[9] The mesh handed to register() was not reproducible, and could abort the process
-------------------------------------------------------------------------------------
Date:        2026-10-04
Fingerprint: Three consecutive builds of the SAME 1,128 instance points gave 9,657 /
             9,655 / 9,656 triangles. Run in a tight loop the call does not vary, it
             terminates the process:

               [ERROR] FEMTree.IsoSurface.specialized.inl (Line 1463)
                       Failed to close loop [6: 85 31 64] | (73439): (684,576,641)
               libc++abi: terminating
               Abort trap: 6

             An abort, not an exception -- no traceback, no cleanup, nothing to catch.

Cause:       `create_from_point_cloud_poisson` defaults to `n_threads=-1`, i.e. every
             core. The multi-threaded isosurface extraction is order-dependent, so the
             triangulation varies run to run and occasionally fails to close a loop.

             Cost beyond the crash: a mesh that changes between builds cannot be diffed
             against a saved input, which is the Debug Rule's whole method, and it makes
             the bundle fingerprint added in [8] meaningless -- rebuilding with identical
             settings would invalidate a pose result that was still perfectly valid.

Fix:         `poisson_mesh()`, with `n_threads=1` pinned and the reason stated at the
             call site so it is not "optimised" back later. Two tests: one spies on the
             kwarg, one asserts the crop keeps the mesh inside its own samples.

Metric before/after:

               distinct vertex hashes over 12 builds   many, then abort  ->  1 / 12
               distinct triangle counts over 12 builds  3 seen in 3 runs ->  1 / 12
               bundle fingerprint over 4 rebuilds       changed          ->  stable
               build wall-clock                                          ->  3.8 s total

Lesson kept: this was found by accident. The fingerprint from [8] changed between two
builds in which nothing had been edited, and the only reason that was noticeable is that
the fingerprint existed at all. A comparability token earns its keep the first time it
disagrees with you -- the instinct to loosen the check instead of chasing the mismatch is
exactly how [S20]/[S21]/[S22] happened on the simulator track.


[10] The kernel ran on the previous bundle, and only its own input check said so
---------------------------------------------------------------------------------
Date:        2026-10-04
Fingerprint: v15's first run printed, before register():

               [input] fingerprint   None
               [input] expected      092fd80f0f0d
               [input] mask px       [695, 803, 655, 941, 901, 834, 954, 953]

             Those are the OLD bundle's masks. Yet the dataset on Kaggle, downloaded
             afterwards, serves 092fd80f0f0d with [7325, 5951, ...] — the upload landed.

Cause:       A race, not a failed upload. `dataset_create_version` returns when the upload
             is ACCEPTED; Kaggle then processes the version asynchronously, and a kernel
             pushed inside that window mounts the last version that was READY. The push
             script pushed the kernel seconds after the dataset call.

Why it matters more than a wasted session: had the kernel not checked its input, it
would have returned ~175.63 deg on the old bundle, and the natural reading — "the
rebuilt input changed nothing, so the Poisson shell geometry is the limit" — would have
been written up as the conclusion of the very experiment designed to test it. A stale
input does not look like an error; it looks like a negative result.

Fix:         Two layers, because either alone has a gap.
               - `wait_for_dataset()` in tools/push_kaggle_pose.py blocks the kernel push
                 until Kaggle SERVES the new bundle — checked by downloading bundle.json
                 from the live dataset and comparing its fingerprint, not by trusting a
                 status field.
               - `EXPECTED_FINGERPRINT`, stamped into fp.py at push time, makes the job
                 refuse a mismatched mount. This is the layer that fired here.
             Also: the poll loop compared str(KernelWorkerStatus.ERROR).lower() to
             "error", never matched, and polled 18 more times after the job had failed.
             grootN1_Robotics/tools/kaggle_baseline.py already stripped the enum prefix;
             now this one does too.

Credit:      the input check exists because a peer session pointed out that an
             unchanged-to-the-decimal 175.63 deg would more likely mean "same input" than
             "same geometry", before the run. It fired on the first attempt.

Metric before/after:  kernel pushed before dataset served     ->  blocked until served
                      stale mount                             ->  refused in-job, logged
                      polls after terminal status             18  ->  0

[13] The pose gate accepted a NaN pose, a non-rotation, and a residual taken on almost nothing
-----------------------------------------------------------------------------------------------
Date:        2026-10-05
Found by:    a review (Codex), with minimal local reproductions — not by any run. Verified
             here before fixing:
               check_pose(pose with NaN translation)        -> accepted
               check_pose(rotation block = 2I)               -> accepted
               depth residual, model covering ~0.4% of the
               observed pixels                               -> 0.00 cm

Cause:       Three independent gaps.
               - Every gate test is `value > threshold`, and NaN fails every comparison, so a
                 NaN pose raised no reason at all.
               - The rotation metric clips its arccos argument for numerical safety, which
                 also maps a matrix that is not a rotation to a small angle: 2I read as 0 deg.
               - The depth residual is a median over the pixels the model covers, with no
                 floor on how many. A residual is evidence only about the pixels it saw.
             And the depth check, the only one independent of the map, was skipped rather
             than required when its inputs were missing.

Fix:         Validity is checked first: non-finite poses and rotation blocks failing
             R^T R = I or det = 1 (tolerance 1e-3) are refused before anything else is
             computed. `depth_agreement` returns coverage with the residual; the gate
             refuses below 50% of the measured pixels under the mask — "the pose must account
             for at least half the observed object", fixed before being run on any recorded
             result (the map pose's 92-98% was already known; the floor was not set from it).
             The main path now REQUIRES depth evidence. 7 tests.

Metric before/after:  NaN pose / 2I / 4%-coverage residual   accepted  ->  refused
                      v15 register() result                  refused   ->  refused (frame 0 cover 64%)
                      v18 prior-tracked result               refused   ->  refused (frame 0 cover 31%)

Also corrected in the same pass, because the review was right: the v18 write-up called a
5-iteration refine call "one step", and said v18 cleared the mesh and trajectory. It did
not — they were built from depth-agreeing points, so the map pose's 3.9 cm is partly by

DESIGN NOTE — where the object mesh comes from
------------------------------------------------
`register(K, rgb, depth, ob_mask)` also needs `mesh`. Model-free mode would require
BundleSDF's NeRF (bundlesdf/mycuda, an optional CUDA build upstream leaves commented out
in build_all.sh). This pipeline avoids it: DROID-SLAM in RGB-D mode gives metric poses,
those fuse into a TSDF, and OpenMask3D cuts a per-instance mesh out of the fused scene.
So `mesh` comes from stages 1-3 and `ob_mask` is the instance mask projected into the
frame. No CAD models, no BundleSDF.

This only holds if DROID ran RGB-D. Monocular poses carry an arbitrary scale, which
would make the mesh the wrong size and the pose confidently wrong — see the `metric`
flag added to droidSLAM_monocular/slam_server.py for how that is surfaced.

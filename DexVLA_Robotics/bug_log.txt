[6] The VLA config delta is a config.json SWAP, not a code path
----------------------------------------------------------------
Date:        2026-08-19
Fingerprint: ValueError: The checkpoint you are trying to load has model type
             `qwen2_vla` but Transformers does not recognize this architecture. This
             could be because of an issue with the checkpoint, or because your version of
             Transformers is out of date.

Two separate things, and the error message misdirects on both:

(a) Stock `Qwen/Qwen2-VL-2B-Instruct` ships `model_type: qwen2_vl`, so
    `AutoConfig.from_pretrained` returns a plain `Qwen2VLConfig` and every VLA field is
    silently dropped. README line 86 says to REPLACE config.json with `docs/config.json`.
    The delta is exactly two things, nothing else:
        model_type:        qwen2_vl -> qwen2_vla
        policy_head_type:  (absent) -> scale_dp_policy
    We keep the original as `config.json.official` beside it.

(b) After the swap the error above appears, which reads like a transformers version
    problem. It is not: `AutoConfig.register("qwen2_vla", ...)` lives at the BOTTOM of
    `qwen2_vla/models/configuration_qwen2_vla.py`, so the model type only exists once
    that module has been imported. Importing `policy_heads` alone is not enough.

Also note `using_film`, `policy_head_config` and `policy_head_size` are READ by
`modeling_qwen2_vla.py` but are NOT declared on `Qwen2VLAConfig`. They exist only because
`train_vla.py::parse_param` injects them after construction. Reading the config class
tells you nothing about them — tools/build_vla.py mirrors that injection.
`ScaleDPPolicyConfig` also stores the action dim as `input_dim`/`output_dim`, not
`action_dim`.

[8] Pad-token counting is occurrence-based, and the pad id IS the bos id
-------------------------------------------------------------------------
Date:        2026-08-19
Latent, not currently triggered — recorded because it fails silently if it ever fires.

`film_forward` computes the start of the observation span as:
    temp = input_ids[i] == 151643   # "pad token id for qwen2_vl"
    start = sum(temp.int())
That COUNTS every occurrence of 151643 anywhere in the sequence; it does not measure the
leading padding run. And `docs/config.json` sets **bos_token_id = 151643** — the same id.
So any occurrence outside the left padding (a BOS, or that id appearing mid-sequence)
shifts `start` and silently mis-slices the observation span.

Not currently triggered: Qwen2's chat template does not prepend BOS. But it is one
tokenizer change away, and the failure is a quietly worse policy rather than an error.
Pinned by `test_pad_count_is_occurrence_based_not_leading_run`, which asserts the CURRENT
behaviour and tells the reader to delete it if upstream switches to a leading-run scan.

ARCHITECTURE NOTES (read from source, not yet exercised)
--------------------------------------------------------
Reasoning injection ("reasoning following"), `modeling_qwen2_vla.py::film_forward`:
  - The prompt span is label-masked with -100 and the reasoning span is not, so a
    bitwise-XOR over `labels == -100` between adjacent positions locates the boundary.
  - `start` skips left padding by counting Qwen2-VL pad tokens (id 151643).
  - observation span -> `input_action_proj`; reasoning span -> `reasoning_action_proj`;
    both are `ActionProjector`, which AdaptiveAvgPool1d's over the sequence so each batch
    element collapses to (1, D) — which is what makes the later `cat(dim=0)` safe.
  - `reasoning_film(input_embeddings, reasoning_embeddings)` is FiLM: reasoning produces
    the scale/shift that modulate the observation embedding. A mean-pooled `identity`
    residual is added afterwards.
  - **FiLM is ZERO-INITIALISED** (scale_fc and shift_fc weights and biases all zeroed),
    so at init the reasoning channel is EXACTLY the identity and contributes nothing. It
    must be learned. Untrained-but-plausible actions are therefore the expected failure
    mode if the reasoning path is mis-wired — it will not crash.
  - At INFERENCE there are no labels, so the model generates first and then FABRICATES a
    labels tensor (-100 over the prompt span, 1 over the generated span) to recover the
    same boundary. Note it passes `input_ids=output_ids` there, and the synthesised
    labels are float rather than long.


[N] Upstream hardcodes CUDA and bf16 in six places — DiVLA could not run anywhere else
----------------------------------------------------------------------------------------
Date:        2026-08-20
Fingerprint: A cascade, each one hiding the next:
               1. AssertionError: Torch not compiled with CUDA enabled
                  (modeling_qwen2_vla.py:1993, `input_ids.to('cuda')`)
               2. RuntimeError: mat1 and mat2 must have the same dtype, but got
                  BFloat16 and Float   (vision block, `.to(torch.bfloat16)`)
               3. AssertionError: Torch not compiled with CUDA enabled
                  (modeling_scaledp.py:428, `torch.randn(...).cuda()`)
               4. NameError: name 'self' is not defined  — my own first fix, which read
                  `self.mlp[0].weight.dtype` inside a @staticmethod

Cause:       `evaluate()` and `forward()` move every tensor with a literal `'cuda'`, and
             `self.computed_type` is assigned `torch.bfloat16` unconditionally. The
             vision block casts its LayerNorm output to bf16 on every call, and ScaleDP's
             timestep embedding both computes and returns in bf16. None of this is
             configurable — it is written into the model definition.

Why it       Both matter beyond the Mac. bf16 is not merely a local inconvenience: the
matters:     T4 this project trains on is Turing (sm_75) and has NO bf16, so the fp16
             path has to work too. A model that can only run in bf16 on CUDA cannot run
             on half the compute this repo actually has.

Fix:         patches/0002 (qwen2_vla) and patches/0003 (scaledp). Every `'cuda'` becomes
             `self.device`; `computed_type` becomes `self.dtype`, which is the dtype of
             the model's own parameters and therefore a no-op on upstream's bf16-on-CUDA
             path; the vision block's cast is dropped (LayerNorm already returns the
             module's dtype); ScaleDP's timestep embedding stays fp32 and `forward` casts
             to the MLP's dtype, since the staticmethod cannot see the module;
             `torch.cuda.empty_cache()` is guarded by `torch.cuda.is_available()`.

Verified:    DiffusionVLA now runs a full forward on CPU: build 11s, inference 3.3s,
             `action.joints (1, 8, 14)`, reasoning string generated. End-to-end over ZMQ
             from the ROS bridge in `tests/test_ros_bridge_against_real_divla.py`,
             6 tests.

Not          These patches are only exercised on the fp32/CPU path. The claim that they
verified:    are a no-op for bf16-on-CUDA is read from the code, not measured. Before any
             DiVLA metric is trusted, run the same forward on a GPU with and without the
             patch and diff the activations — the patch is in patches/ precisely so
             pristine upstream stays available for that diff.
